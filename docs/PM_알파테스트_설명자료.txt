안테나 예지보전 알파 테스트 설명 자료
=====================================

1. 프로젝트 목적
----------------

이 기능은 항만에서 사용하는 안테나의 센서 데이터를 지속적으로 관찰하여,
고장이 발생하기 전의 이상 징후를 발견하고 관리자에게 점검 시점을 알려주는
예지보전 시스템이다.

단순히 고장 여부만 표시하는 것이 아니라, 관리자가 과거 센서 흐름과 모델의
판정을 함께 확인하고 실제 점검 필요 여부를 판단할 수 있도록 대시보드,
고장·정비 이력, 카카오톡 알림 기능을 구성했다.


2. 고장 판단에 사용하는 데이터
-------------------------------

안테나별로 다음 8개 핵심 센서를 사용한다.

- 전압
- 신호 세기
- 통신 성공률
- 응답 시간
- 재시도 횟수
- 연결 끊김 횟수
- 패킷 손실률
- 오류 횟수

온도와 트래픽 부하는 화면에서 참고 정보로 볼 수 있지만, 현재 핵심 고장
판정에는 사용하지 않는다.


3. 센서 이상 판단 방식
----------------------

모든 안테나에 동일한 절댓값을 적용하지 않는다. 안테나별 최초 30일 데이터를
정상 기준 구간으로 삼고, 센서값의 3시간 이동평균을 계산한다.

장비별 센서 분포에서 1% 극단값을 정상 한계로 사용한다.

- 낮아질수록 이상인 센서:
  전압, 신호 세기, 통신 성공률

- 높아질수록 이상인 센서:
  응답 시간, 재시도 횟수, 연결 끊김 횟수, 패킷 손실률, 오류 횟수

특정 시점의 3시간 평균이 해당 안테나의 정상 한계를 벗어나면 이상 센서
1개로 계산한다. 이 방식은 안테나마다 평상시 센서 수준이 다른 점을 반영한다.


4. 상태 판정 기준
-----------------

- 정상: 이상 센서 0~2개
- 의심: 이상 센서 3~4개
- 위험: 이상 센서 5개 이상
- 고장 예상: 이상 센서 5개 이상이 6시간 연속 지속
- 실제 고장: L2 모델 양성 AND 이상 센서 7개 이상
- 정상 회복: 이상 센서 2개 이하가 6시간 연속 지속

센서 하나가 일시적으로 튀었다고 바로 고장으로 판단하지 않는다. 여러 센서가
동시에 이상을 보이는지, 그 상태가 일정 시간 지속되는지를 함께 확인한다.

또한 '고장 예상'은 반드시 고장이 발생한다는 뜻이 아니다. 복수 센서의 이상이
일시적인 변동을 넘어 지속되었으므로 점검이 필요한 전조 상태라는 뜻이다.


5. 사용 모델과 선정 이유
------------------------

현재 고장 판정 모델로 Balanced L2 Logistic Regression을 사용한다.

선정 이유:

- 구조가 단순하여 판정 방식을 설명하기 쉽다.
- 검증 구간에서 높은 성능을 보였다.
- 이상 센서 7개 조건과 결합했을 때 정상 데이터 오탐이 없었다.

모델 결과만으로 고장을 확정하지 않는다. 모델이 고장으로 판정하고 동시에
8개 중 7개 이상 센서가 이상일 때만 현재 고장으로 확정한다.

24시간 이내 고장 예측을 위한 Elastic Net과 전조 진행 여부를 판단하기 위한
Random Forest 등도 실험했지만, 표본 부족과 과적합 문제로 현재 운영 판정에는
채택하지 않았다.


6. 데이터 및 시스템 구성
-------------------------

처리 흐름:

CSV 또는 향후 기기 데이터
 -> DB 센서 데이터 적재
 -> 이상 센서와 모델 판정 확인
 -> 고장 예상·실제 고장·수리 완료 사건 생성
 -> 대시보드 그래프와 점검·정비 이력 표시
 -> 고장 예상 및 실제 고장 시 카카오톡 알림

DB는 다음 세 테이블을 중심으로 구성했다.

- pm_equipment:
  24개 안테나의 코드, 위치, 운영 여부 등 기본정보

- pm_sensor_data:
  시간별 센서값, 이상 센서 개수, 모델 확률과 상태 판정

- pm_event:
  고장 예상, 실제 고장, 수리 완료 및 카카오 알림 처리 결과

CSV는 화면이 직접 읽는 것이 아니라 백엔드 적재 API를 통해 DB에 저장한다.
화면은 API를 통해 DB의 안테나 목록, 센서 시계열, 사건 이력을 조회한다.


7. 대시보드 시연 순서
---------------------

1) 시연용 안테나를 선택한다.
2) 시간 재생 기능으로 센서값의 변화 과정을 보여준다.
3) 복수 센서 이상이 6시간 지속되면서 고장 예상 상태로 바뀌는 것을 확인한다.
4) 점검·정비 화면에 고장 예상 사건이 생성되는 것을 보여준다.
5) 고장 예상 카카오톡 알림이 발송되는 것을 확인한다.
6) L2 모델 양성과 7개 이상 센서 이상이 함께 발생하면 실제 고장으로 확정된다.
7) 실제 고장 사건과 두 번째 카카오톡 알림을 확인한다.
8) 정비 이후 센서가 안정되면 수리 완료와 회복 상태를 확인한다.

과거 CSV에서 생성된 사건은 이미 지나간 기록이므로 실제 카카오톡을 발송하지
않는다. 시연용 재생을 정상 방향으로 진행해 사건 시점을 처음 통과할 때만
알림 요청을 만들며, 시간을 뒤로 이동할 때는 중복 알림을 보내지 않는다.


8. 알파 테스트에서 확인할 사항
-------------------------------

- 정상, 의심, 위험, 고장 예상, 실제 고장 단계가 이해하기 쉬운가?
- 고장 예상 시점을 그래프의 센서 변화로 납득할 수 있는가?
- 어떤 센서가 문제인지 쉽게 찾을 수 있는가?
- 고장·수리 이력이 시간 순서대로 이해되는가?
- 카카오 알림의 내용과 발송 시점이 적절한가?
- 관리자가 점검 필요 여부를 판단하는 데 도움이 되는가?
- 화면에 불필요하거나 지나치게 자세한 정보가 있는가?


9. 실험 결과를 설명할 때의 주의점
----------------------------------

합성 데이터 내부 검증에서는 제공된 고장 행 36개와 고장 사건 12건을 모두
포착했고 정상 행 오탐은 없었다.

고장 전조 기준의 보지 않은 테스트 구간 사건 단위 결과는 Precision 0.667,
Recall 1.000, F1 0.800이며 실제 고장 4건을 모두 포착했다. 그러나 고장 없이
회복된 전조도 2건 포함되었다.

사건 표본이 적고 합성 데이터를 사용했으므로 이 수치를 실제 현장 전체의
일반화된 성능으로 단정해서는 안 된다. 현재 단계는 상용 모델의 완성을
주장하는 단계가 아니라, 판정 기준과 관리자 화면, DB 적재, 이력 관리,
알림 흐름을 검증하는 알파 테스트 단계이다.


10. 발표용 핵심 문장
--------------------

“장비별 정상 범위를 벗어난 복수 센서의 개수와 지속시간으로 고장 전조를
판단하고, 실제 고장은 L2 로지스틱 회귀 모델과 7개 이상 센서 이상 조건이
동시에 충족될 때 확정하는 안테나 예지보전 시스템입니다.”


11. 짧은 발표 예시
------------------

“저희는 항만 안테나에서 수집되는 8개 핵심 센서를 이용해 예지보전 기능을
구현했습니다. 안테나마다 평상시 상태가 다르기 때문에 최초 30일 데이터를
장비별 정상 기준으로 사용했고, 3시간 이동평균이 정상 범위를 벗어난 센서의
개수를 계산했습니다. 이상 센서가 5개 이상인 상태가 6시간 지속되면 고장
예상으로 판단해 관리자에게 점검 알림을 보냅니다. 실제 고장은 모델의 양성
판정과 7개 이상 센서 이상이 동시에 발생할 때만 확정하여 단일 센서 변화나
모델 결과만으로 고장을 단정하지 않도록 했습니다. 판정 결과는 DB에 저장되고,
대시보드 그래프와 고장·정비 이력에서 확인할 수 있으며 고장 예상과 실제 고장
시점에는 카카오톡 알림을 보낼 수 있도록 구성했습니다. 현재는 합성 데이터를
이용한 알파 테스트 단계로, 현장 적용 전 화면의 이해도와 알림 시점, 판정 흐름의
적절성을 검증하는 것이 목적입니다.”
