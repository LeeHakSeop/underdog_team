# 안테나 예지보전 기능 설계

## 1. 목적과 용어

이 기능은 항만 운영 설비의 상태 데이터를 수집하고, 고장 위험을 예측하여 점검과 정비로 연결하는 관리자용 기능이다.

- 첫 번째 설비 유형의 사용자 표시명은 **안테나 예지보전**으로 통일한다.
- 내부 식별 코드는 `ANTENNA`를 사용한다.
- 두 번째 설비 유형은 데이터가 도착할 때까지 `TYPE_2` 자리만 유지하고 화면에서는 **준비 중**으로 표시한다.
- 합성 CSV V3와 `pm_visualization_bundle_v3`는 화면과 데이터 흐름을 검증하는 개발용 데이터로 사용한다.
- 원본 CSV의 `risk_score`, `risk_level`, `failure_within_7d`, `rul_hours`는 합성 공식 또는 미래 정보이므로 운영 화면 판정에서 제외한다.
- 화면은 번들의 장비별 센서 한계, 이상 센서 수, 6시간 지속 여부, 현재고장 후보 모델 결과로 생성된 `operational_state`를 사용한다.

## 2. 사용자 흐름

```text
관리자 로그인
  -> 예지보전 메뉴
  -> 설비 유형 선택(안테나 / 준비 중)
  -> 전체 위험 현황 확인
  -> 위험 설비 선택
  -> 센서 추이와 예측 근거 확인
  -> 경보 접수
  -> 점검·정비 등록
  -> 처리 완료 및 이력 확인
```

## 3. 화면 구조

사이드바에는 `예지보전` 메뉴 하나를 추가하고, 예지보전 화면 안에서 하위 기능을 탭으로 전환한다. 설비 유형 선택 버튼은 모든 하위 화면 상단에 공통으로 둔다.

### 3.1 공통 설비 유형 선택

| 버튼 | 초기 상태 | 동작 |
|---|---|---|
| 안테나 예지보전 | 활성 | 안테나 데이터와 화면 표시 |
| 두 번째 설비 | 비활성·준비 중 | 데이터 계약이 확정되면 활성화 |

유형 선택은 URL의 `type` 쿼리와 Pinia 상태에 함께 보관한다. 새 유형이 추가되어도 화면 구조와 API 호출 코드는 그대로 재사용한다.

### 3.2 대시보드

- 전체 설비와 정상·의심·위험·고장 예상·고장 상태 수
- 운영 상태 분포
- 최근 24시간 상태 변화
- 점검 필요 설비 목록
- 최근 경보와 예정 정비
- 데이터 기준 시각과 사용 모델 정보

### 3.3 설비 현황

- 설비 목록 검색, 유형·위치·상태 필터, 정렬, 페이지 이동
- 설비 등록, 상세 조회, 수정, 사용 중지
- CSV 직접 행 삭제와 달리 운영 데이터는 이력 보존을 위해 기본적으로 논리 삭제

### 3.4 설비 상세

- 기본 정보와 현재 위험 등급
- 시간별 센서 추이
- 최신 예측 확률과 예측 기준 기간
- 경보 발생 근거
- 경보·점검·정비 이력

### 3.5 센서 데이터

- 설비와 기간별 측정값 조회
- 개발·관리 목적의 단건 등록 및 수정
- CSV 일괄 가져오기는 별도 작업으로 분리
- 운영 원본 센서 데이터의 삭제는 관리자 확인 후 수행

### 3.6 경보 관리

- 위험 경보 목록과 상세
- `OPEN -> ACKNOWLEDGED -> IN_PROGRESS -> RESOLVED` 처리 흐름
- 담당자, 조치 메모, 처리 시각 기록
- 같은 설비의 짧은 시간 내 반복 경보는 하나의 사건으로 묶을 수 있도록 설계

### 3.7 점검·정비 관리

- 점검·정비 일정 등록, 조회, 수정, 취소
- 예방점검·수리·부품교체 등 작업 유형
- 예정·진행·완료·취소 상태
- 경보 및 설비와 연결하여 조치 결과 추적

### 3.8 모델 정보

- 모델명·버전·적용 시각·예측 기간
- PR-AUC, Precision, Recall, F1, F2 등 검증 결과
- 운영 임계값과 경보 정책
- 모델 선택이 확정되기 전에는 합성 데이터 실험 결과임을 명확히 표시

## 4. 공통 데이터 영역

두 번째 설비 유형을 수용하기 위해 공통 영역과 유형별 측정값을 분리한다.

| 영역 | 역할 |
|---|---|
| 설비 유형 | `ANTENNA`, 향후 두 번째 유형 등 화면·데이터 구분 |
| 설비 | 설비 코드, 명칭, 위치, 운영 상태 |
| 센서 측정 | 수집 시각과 유형별 측정값 |
| 상태 판정 | 운영 상태, 이상 센서 수, 현재고장 확률, 모델 정보, 판정 근거 |
| 경보 | 예측 결과에서 생성된 운영 사건과 처리 상태 |
| 정비 이력 | 점검·정비 일정과 실제 조치 결과 |
| 모델 버전 | 모델과 임계값, 평가 지표의 적용 이력 |

## 5. 구현 순서

1. 화면·기능 범위와 용어 확정
2. PostgreSQL 테이블과 REST API 계약 작성
3. 관리자 메뉴, 라우터, 공통 유형 선택기, 빈 화면 구현
4. 설비 및 센서 데이터 CRUD 구현
5. 경보 및 점검·정비 CRUD 구현
6. 예측 결과와 대시보드 집계 연결
7. 두 번째 설비 유형 확장 지점 검증
8. 통합 테스트와 사용자 학습 문서 작성

## 6. 이번 구현에서 학습할 흐름

```text
Vue 화면
  -> Pinia Store
  -> API 모듈
  -> Spring Controller
  -> Service
  -> MyBatis Mapper
  -> PostgreSQL
  -> 응답 DTO
  -> Pinia Store
  -> Vue 화면 갱신
```

각 단계가 끝날 때 다음 세 가지를 함께 남긴다.

1. 먼저 읽을 핵심 파일 3개
2. 요청부터 화면 표시까지의 데이터 흐름
3. 직접 해볼 수 있는 작은 수정 과제

## 7. 화면 구성 변경 기록

### 2026-08-06 변경 전 상태

- 상단 요약 영역은 `관찰 중인 시점`, `데이터 상태`, `합성 위험 점수`, `주요 이상 지표`의 4칸이었다.
- `주요 이상 지표`는 현재값이 임시 주의 기준을 가장 크게 벗어난 지표 하나를 자동 선택했다.
- 선택된 지표와 직전 24시간 평균 대비 변화량을 표시했고, 누르면 해당 그래프로 이동했다.
- 아래 지표 버튼은 지표명과 현재값만 표시했다.

이 구성이 더 적합하다고 판단되면 위 상태로 되돌릴 수 있다.

### 2026-08-10 점검·정비 화면 시제품

- 변경 전 `점검·정비` 탭은 구현 예정 안내만 표시하는 빈 화면이었다.
- 시제품은 합성 CSV V3의 정비 이벤트 12건을 전체·안테나별로 조회한다.
- 초기 시제품은 정비 기록별 여러 코멘트의 등록·수정·삭제를 브라우저 저장소로 시험했다.
- 시제품이 적합하지 않으면 `AdminPredictiveMaintenanceView.vue`의 `MaintenanceRecordBoard` import와 조건부 렌더링을 제거하여 기존 빈 화면으로 되돌린다.
- 독립 컴포넌트 `MaintenanceRecordBoard.vue`를 사용하므로 대시보드와 시계열 그래프에는 영향을 주지 않는다.

### 2026-08-10 알파 메뉴 단순화

- 알파 화면에는 `대시보드`, `점검·정비` 두 메뉴만 표시한다.
- `설비 현황`, `센서 데이터`, `경보 관리`, `모델 정보`는 삭제하지 않고 `predictiveMaintenanceFutureSections`에 보관한다.
- VMS·실제 모델·설비 CRUD를 연결하는 베타 단계에서 보관된 메뉴를 `predictiveMaintenanceSections`로 다시 옮기면 기존 6개 탭 구성으로 복원된다.

### 2026-08-11 합성 CSV V3 적용

- 화면용 데이터 기준을 `predictive_maintenance_timeseries_synthetic_v3.csv`로 변경한다.
- 기존 CSV는 삭제하지 않고 비교·복구용으로 보존한다.
- 기존 데이터로 되돌릴 때는 데이터 생성 스크립트에 기존 CSV 경로를 인자로 전달하고 화면의 데이터 버전 표시를 함께 되돌린다.

### 2026-08-11 운영 정책 번들 적용

- 화면용 원본을 `pm_visualization_bundle_v3/01_dashboard_timeseries.csv`로 변경한다.
- `risk_score` 버튼과 40점·70점 임시 기준을 제거한다.
- 상단에는 운영 상태, 이상 센서 수, 현재고장 모델 확률을 표시한다.
- 센서 버튼과 그래프 배경은 `04_sensor_limits_by_equipment.csv`의 안테나별 정상 한계를 사용한다. 트래픽 부하와 온도는 상태 판정에서 제외하는 참고 지표다.
- 운영 상태는 `정상 -> 의심 -> 위험 -> 고장 예상 -> 고장` 흐름을 사용하며, 고장 후에는 회복 상태를 별도로 표시한다.
- 고장 예상은 이상 센서 5개 이상이 6시간 지속될 때 진입한다. 현재 고장은 L2 모델 양성과 이상 센서 7개 이상을 함께 만족해야 한다.
- 되돌릴 때는 생성 스크립트와 `AntennaHistoryPlayback.vue`를 이 변경 전 버전으로 복원하고 기존 V3 JSON을 다시 생성한다.

### 2026-08-12 고장 예상 알림 기준

- 카카오 알림 사건은 설비가 `FAILURE_EXPECTED` 상태로 처음 전이된 시점에 생성한다.
- 같은 고장 전조가 유지되는 동안 반복 발송하지 않고 상태 진입당 한 번만 발송한다.
- 화면에는 발송 기준 시각과 이상 센서 수를 표시한다. 현재 시제품은 `DEMO_NOT_SENT` 상태로 실제 카카오 메시지를 보내지 않는다.
- ANT-002·ANT-009처럼 고장 전 `FAILURE_EXPECTED` 상태가 없었던 사례는 알림을 인위적으로 생성하지 않고 `사전 알림 없음 · 급작 고장`으로 표시한다.
- `고장 예상` 없이 바로 `고장`이 된 사례도 모델 적용 누락이 아니라 상태 판정 결과로 기록한다.

### 2026-08-12 고장·정비 사건 화면 개편

- 관리자 코멘트 입력·수정·삭제와 브라우저 임시 저장 기능을 제거한다.
- 점검·정비 상세는 `고장 예상 및 카카오 알림 -> 실제 고장 -> 수리 완료` 순서로 표시한다.
- 급작 고장은 첫 단계를 `사전 알림 없음`으로 표시하여 사전 예측 성공 사례와 구분한다.
- 별도의 코멘트 테이블은 만들지 않고, 고장 예상·고장·수리·알림 결과를 사건 기록으로 관리한다.

### 2026-08-12 시연용 현재 시각 재생

- 기존 24대는 과거 기록으로 유지하고 과거 사건을 이유로 새 알림을 발송하지 않는다.
- 기존 24대의 고장 예상·실제 고장 알림 사건은 `SUPPRESSED_PAST`로 기록해 규칙 적용 여부와 과거 발송 억제를 구분한다.
- `시연용 안테나`는 ANT-018의 고장 사례를 복제해 고장 예상 시각을 현재 시각 근처로 이동한다.
- 그래프 재생이 고장 예상 시점을 처음 통과하면 `FAILURE_EXPECTED`, 실제 고장 시점을 통과하면 `FAILURE` 카카오 알림 요청을 각각 한 번 생성한다.
- 점검·정비 화면의 시연용 기록은 관찰 시점에 맞춰 대기, 고장 예상, 고장 발생, 수리 완료 순서로 갱신된다.
- 실제 발송 여부는 백엔드 카카오 연동 결과에 따라 표시하며, 연동 전에는 `DEMO_REQUESTED`로만 기록한다.
